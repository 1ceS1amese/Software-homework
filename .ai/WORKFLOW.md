# WORKFLOW.md

本项目采用**契约先行、纵向切片、证据驱动**的五阶段工作流。每个阶段有明确门禁（Gate），未过 Gate 不得进入下一阶段。

## 阶段总览

| 阶段 | 名称 | 门禁（Gate） |
|---|---|---|
| S0 | 盘点与约束基线 | 无既有资产被破坏；授权边界写进 `PROJECT.md` |
| S1 | 需求与范围 | 角色/流程/范围外/BR 编号全部落纸 |
| S2 | 契约设计（库表 + 接口） | 表名、字段、枚举、端点在下游文档中被逐字复用 |
| S3 | 方案细化（前后端/非功能/测试/部署） | 每条 BR 在测试方案中有对应用例 |
| S4 | 实施与验证 | 最小纵向切片端到端跑通 + 证据落盘 |

当前处于 **S3 已完成 / S4 未授权**。

---

## S0 盘点与约束基线

动作：读 `AGENTS.md`、`.ai/*`；扫描入口、构建、配置、测试、CI、部署现状；记录环境基线。
产出：`PROJECT.md` §3 技术栈、§6 授权、§7 环境基线。
禁止：重写已有文件、覆盖用户未提交改动。

## S1 需求与范围

动作：识别角色 → 画核心流程 → 定业务规则（BR-xx）→ 划范围外 → 写可观察验收。
产出：`docs/00`、`docs/10`。
门禁：每条 BR 必须能用一句"给定…当…则…"验证；出现"可能需要"类模糊描述即打回。

## S2 契约设计

动作：**先**定数据契约（`docs/02`），**再**定接口契约（`docs/05`）。
产出：`docs/02`、`docs/05`。
门禁：
- 每张表有主键、审计字段、逻辑删除策略、索引理由；
- 枚举值集中在一处定义，其余文档引用不重定义；
- 每个写接口标明幂等性、事务边界、权限要求、错误码。

## S3 方案细化

动作：把契约翻译成实现方案（模块职责、页面结构、测试策略、部署拓扑）。
产出：`docs/01`、`docs/03`、`docs/04`、`docs/06`、`docs/07`、`docs/08`、`docs/09`、`docs/11`。
门禁：BR ↔ 测试用例 ↔ 页面 三向可达（每条 BR 至少 1 个用例 + 1 个界面触点）。

## S4 实施与验证（需用户明确授权）

1. 先做 `TASKS.md` C-1 骨架（能 `mvn -v` / `pnpm dev` 起来）。
2. **纵向切片优先**：`docs/09` §2 定义的三条主链路先通，禁止先做全部 CRUD 再联调。
3. 每个小步必须：改真实文件 → 跑检查 → 修失败 → 把命令与输出存到 `docs/evidence/`。
4. 并发路径必须有集成测试证明（Testcontainers 起真实 MySQL，跑并发选课，断言不超卖）。
5. 异常、越权、超预算、状态终止（退课/成绩发布后改分）必须有独立用例。

---

## 证据规则（贯穿 S4）

- ✅ 允许："已在本机跑通 `mvn test`，17/17 通过，输出见 `docs/evidence/unit-2025xxxx.log`"
- ❌ 禁止："功能应该没问题"、"可直接上线"、"已部署"

## 回退规则

任何技术假设（AS-xx）被证伪时：
1. 不改已定稿的上游契约；
2. 按假设表中的"回退方案"执行；
3. 在 `docs/11` 把该 AS 状态从 `假设` 改为 `已证伪-已回退`，写明日期与新方案；
4. 在 `HANDOFF.md` §3 决策表同步更新。
