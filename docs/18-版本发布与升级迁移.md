# 18 版本发布与升级迁移

适用本项目已授权的独立演示实例。运维演练采用与生产运行相同的备份、恢复校验和发布回退方式，但不代表真实高校生产容量或安全合规验收。其他服务器、既有生产库和付费资源必须另行授权。

## 1. 版本与兼容

前后端版本必须一致，正式版采用 `MAJOR.MINOR.PATCH`。修复使用 PATCH，兼容新增使用 MINOR，不兼容业务变更使用 MAJOR；API 破坏性变更按 docs/05 升 `/api/v2`。每次正式发版必须更新根目录 `CHANGELOG.md`、发布标签和升级说明，禁止重写已经发布的标签。

本版 `1.0.0` 保持 Flyway V1～V4 的内容与校验值，新增 V5 的三项认证配置行，不增加表或改变数据字段；升级时必须正常执行 Flyway validate，禁止 `repair` 或删除历史记录绕过失败。默认演示数据不应导入真实机构生产库。

| 调用 | 标准 `/api/v1` | 历史根路径（前端 `/api` 代理） |
|---|---|---|
| 登录 | `{accessToken,tokenType,expiresIn,user}` | JWT 字符串 |
| Long ID | 字符串 | 保留原数字返回 |
| 退课路径参数 | 选课关系 ID | 教学班 ID |
| 批量存成绩 | `POST /teaching-classes/{id}/grades`，`{items:[...]}` | `PUT /grades/class/{id}`，直接数组 |
| 发布成绩 | `POST /teaching-classes/{id}/grades/publish`，`{confirm:true}` | 原发布调用保留 |
| 健康检查 | 带标准响应、版本和源码提交 | 原 Actuator 状态对象 |

接口与业务定义以 docs/00、02、05 为准；冲突处理与限制登记在 docs/11。已发布 JWT 可继续按签名和账号版本验证；账号被修改时旧令牌立即失效。CSV 预览令牌不持久化，升级、重启或成绩/配置变更后必须重新预览。

## 2. 从干净提交生成发布包

以下命令在本地仓库根目录执行，工具链见 docs/12；禁止 Docker。

```bash
source scripts/env.sh
./scripts/test.sh all
python3 -m unittest discover -s tests
python3 scripts/package-release.py
```

打包器要求工作区干净，构建后端并运行其测试、构建前端，且只复制 Git 跟踪的原生模板。Vite 禁止自动读取 `.env`；发布构建剔除继承的 `CSMS_`、`SPRING_`、`VITE_` 参数，不使用本地数据库。构建需要已经安装的锁定依赖；清洁环境先按 README 安装。

输出在忽略目录 `.local/releases/`：`<版本>-<源码短提交>.tar.gz` 和摘要文件。包内只允许 `app.jar`、`frontend/`、`native/`、`manifest.json`。清单记录源码提交、源码树、版本和每个文件的 SHA-256。禁止加入 `.env.local`、私钥、数据库文件、工具链、node_modules 或日志。

必须在两套独立原生 MySQL 上执行完整验收，分别记录源码与 JAR 摘要。若检查发现问题，应独立修复并复验，第二轮必须覆盖最终应用代码；其后仅调整运维模板时，必须验证应用字节等价并单独复验运维步骤：

```bash
python3 scripts/acceptance.py --skip-build
python3 scripts/acceptance.py --skip-build
```

验收结果必须记录真实数量、失败修复和平台边界。三个浏览器引擎与三个视口不等于所有操作系统或真实移动设备认证。

## 3. 升级前备份与恢复演练

以下命令在原授权服务器执行；文件路径均为本项目独立目录。应先核对当前发布链接、自有服务、磁盘空间和上一版本清单。禁止操作其他服务或共享数据库的数据目录。

将已校验发布包解压到新目录 `/opt/csms/releases/<release-id>`，拒绝绝对路径、`..`、符号链接与清单外文件，然后执行：

```bash
read -r -p "已核验的发布目录（绝对路径）：" csms_release_dir
python3 "$csms_release_dir/native/verify-release.py" "$csms_release_dir"
python3 "$csms_release_dir/native/backup.py" --verify-restore
```

备份工具先验证专用客户端配置权限及 MySQL 的实际数据目录。恢复验证会短暂停止自己的后端，在一致状态计算全部表摘要、备份，再恢复服务；备份仅导入全新 `csms_restore_*` 临时库。必须逐表校验行数和内容摘要完全一致，最后清理该临时库。不得覆盖现有库。普通定时备份使用单事务，无需停止后端。

备份和回执位于 `/var/backups/csms/`，目录 700、文件 600。必须检查 `restoreVerified=true`，并记录备份摘要。备份包含敏感数据，禁止上传 Git 或公开下载；至少保留升级前、升级后已验证备份和所需日备份，结合磁盘空间定期清理过期副本。

## 4. 切换、观察与回退

先以旧站点为基础更新本项目的 Nginx 配置；只替换自己的 vhost。必须分别保留 `/api/v1/` 原前缀与旧 `/api/` 去前缀规则，两种登录入口均限流；`nginx -t` 成功后才允许 reload。更新外部 `application-demo.yml` 的滚动日志配置时，保留既有 `backend.env` 与 TLS 私钥。

```bash
read -r -p "已验证备份文件（绝对路径）：" csms_backup_file
python3 "$csms_release_dir/native/activate-release.py" \
  "$csms_release_dir" --backup-file "$csms_backup_file"
```

脚本核验新旧发布清单、备份路径和权限，原子替换 `current`，仅重启 `csms-backend`。健康检查超时会恢复旧链接并重启旧版；人工回退采用相同命令，将目标换成上一份已验证发布。不得以删库或强制 Git 回退代替版本切换。

本次数据库结构不变，因此旧版可读取同一数据。若未来存在不兼容迁移，必须在升级前设计恢复到新实例的方案，不得直接在原生产库执行逆向迁移。回退演练后应再次切换到新版本并复核。

成功标志必须包括：

- 私有 CA 严格验证 IP 与 TLS 1.2/1.3，SPA 深层路由刷新正常。
- `/api/v1/actuator/health` 的版本与源码提交匹配清单；旧健康入口可用。
- 三角色登录、管理写入、选退课与名单联动、成绩发布/解锁、CSV 导入和审计。
- 业务计数对账为空，已有账号与必要演示数据保留。
- 仅重启本项目后端和数据库后数据摘要一致；不得重启承载其他服务的整台服务器。

## 5. 日常运维

原生模板提供 `csms-backup.service`、`csms-backup.timer`。备份脚本必须复制到独立固定目录，避免回退到不包含该脚本的旧发布后导致备份失效。将单元安装到 `/etc/systemd/system/` 后执行：

```bash
install -d -m 755 /opt/csms/operations
install -m 644 /opt/csms/current/native/backup.py /opt/csms/operations/backup.py
systemctl daemon-reload
systemctl enable --now csms-backup.timer
systemctl start csms-backup.service
systemctl status csms-backup.service --no-pager
systemctl list-timers csms-backup.timer --no-pager
```

定时规则为服务器系统时区每天 03:30，最多随机延迟五分钟。必须检查实际执行回执，不能仅以 timer 已启用声称备份成功。自动备份不等于恢复演练，升级前仍必须执行 `--verify-restore`。

后端日志按 20MB 分卷、保留14天、上限500MB；Nginx 模板用独立 logrotate 配置，安装前应确认没有对同一文件重复轮转，执行 `logrotate --debug` 验证。`copytruncate` 在复制截断的瞬间存在小范围日志遗漏可能，关键审计以数据库记录为准。

日志排查使用 `journalctl -u csms-backend`、`journalctl -u csms-mysql` 和 `/var/log/csms/`。禁止公开包含个人信息的原始日志、请求认证状态或备份。证书信任、续签与公网 HTTP 入口边界见 docs/17。

## 6. Git 发布与同步验收

功能分别提交后，完成所有检查再正常合并到 `main`，创建 `v1.0.0` 注释标签并推送，GitHub Release 应引用该标签。已授权原仓库，不创建替代仓库，不强推。

最终必须通过远端重新克隆的镜像核验全部分支、标签、提交历史与可达对象，同时比较受控文件内容和模式。发布构建的源码提交可能早于之后追加的验收文档提交；两者必须分别记录，禁止混淆“部署源码提交”与“仓库最新说明提交”。
